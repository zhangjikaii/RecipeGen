# 食谱检索与生成系统

RecipeGen 从 Neo4j 中读取原食谱及来源，默认执行 **BM25 关键词候选＋图谱先筛的 E5 语义候选＋Cypher 图谱条件候选 → 合并核验 → 双排名 RRF → 一阶图谱证据回读 → 有界上下文 → DeepSeek API 重排与问答**。食谱探索只检索；厨神交流由模型判断是否检索，再直接回答或依据食谱证据回答。

## 数据与运行条件

开发机器使用 `RUOXUAN123/RecipeGen` 的 `test.zip`、`test-video.zip`，固定 revision `2506260d8cb193ecdb18ac31fc725ffec43f6602`。基础图谱包含 5,898 条分来源食谱记录、44,802 行原步骤、296 个规则食材实体，复用 5,898 个食谱级 E5 向量。记录保留不同归档身份，未声称已去重为独立菜品。

源码仓库不携带真实语料、图谱、向量、模型权重、私密配置和原始运行报告。新环境需按 [测试集图谱构建](测试集图谱构建.md)重建并导入，再按 [GraphRAG 设计](GraphRAG设计.md)准备文本模型及完整索引。`data/example_graph.json` 是另一组兼容演示的人工数据，不能用于修复真实图谱连接。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
# 在 .env 中填写自己的 Neo4j 连接和 DeepSeek API 配置。
chmod 600 .env
python -m recipegen serve --host 127.0.0.1 --port 8765
```

Neo4j 需先保持可用。完整 `NEO4J_*` 配置优先；历史环境也可读取权限为 `600` 的 `.runtime/active-neo4j.json` 或 `.runtime/local-neo4j.json`。新克隆不包含这些文件。应用只读检索要求唯一已激活且已验证的固定测试构建，不会在连接失败后自动切换人工图谱。

打开 [本地首页](http://127.0.0.1:8765/)或 [API 文档](http://127.0.0.1:8765/docs)。也可用 `scripts/manage_recipegen_system.py` 的 `start`、`status`、`stop` 管理服务；停止前核对进程命令与项目目录。`/health` 只表示服务响应，真实数据与模型状态见 `/api/system/status`。启动网页不会启动图片或视频批处理。

## 两个网页入口

- **食谱探索 `/?view=explore`：**输入想用和不想用的食材，调用 `/api/search` 的 `hybrid` 路径，直接返回食谱及原步骤、来源。此入口不调用 LLM。
- **厨神交流 `/?view=chat`：**只输入提示词，可多轮追问。DeepSeek 根据当前问题与最近对话选择 `respond` 或 `retrieve`；普通烹饪交流直接回答，具体食谱查询进入检索、重排与证据问答。状态与消息合同见 [厨神交流](厨神交流.md)。

旧 `/explore`、`/compose` 地址继续兼容；食谱详情为 `/recipes/{recipe_id}`。

## 检索方法

1. **条件解析。** 探索提供所需及排除食材；聊天由 DeepSeek 输出经过 JSON 校验的独立问题与条件数组。中文别名映射为规范名，所需食材之间为 AND，单项别名为 OR，排除食材为集合差。模型不能提供任意 Cypher。
2. **关键词候选 A。** 标题与全部步骤形成原食谱全文投影，本地 Okapi BM25 使用 `k1=1.5`、`b=0.75`，NFKC、小写、英文词及中文单字分词。存在正向食材时使用生产英文别名展开，否则使用问题词面。全库取正分 Top50。
3. **图谱候选 C。** 固定参数化只读 Cypher 核验 `HAS_INGREDIENT`，返回全部满足所需及排除条件的食谱和有效文本向量；此阶段不截取 TopK。
4. **语义候选 B。** 本地 `intfloat/multilingual-e5-small` 编码完整问题，只在 C 的 live 向量矩阵内计算 float32 精确余弦并取 Top50，不先做全库 ANN 再过滤。
5. **合并、核验与 RRF。** 合并 A、B、完整无序 C，再核验硬条件。在最终合法池重算 BM25 正分排名与 E5 排名，使用 `RRF=1/(60+rank_BM25)+1/(60+rank_E5)`；BM25 为零时没有该路贡献，同分按稳定食谱 ID 排序。**图谱没有第三份排名；完整 C 决定当前合法池，BM25/E5 影响排序，而不扩大池。**
6. **证据回读。** RRF 后才为内部最多 50 条候选执行一阶查询，回读 Ingredient、全部有序 Step 和 Source，再核对构建、原文哈希、步骤归属与来源。此扩展补全已选食谱证据，不引入新食谱。搜索最终返回请求的 1～20 条。

E5 固定 revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`，输出 384 维。食谱输入为 `passage: `＋标题＋有序步骤；问题为 `query: `＋问题，采用 attention-mask 平均池化及 L2 归一化。512-token 上限使历史 95 条长食谱编码截断；图谱和问答仍保留完整原步骤。网页不要求先切步骤块；保留的分块 CLI 是独立实验。

默认 `hybrid` 返回 `method=graph_first_bm25_e5_rrf`、`rrf_k=60`、`approximate_search=false`，保留种子、候选池、双排名及阶段 trace。`graph_candidate_count=scored_recipe_count` 用于检查完整图条件候选评分。原 ONLINE 向量索引用于身份及就绪检查，本链路不执行 ANN。缺少有效向量、构建或原文身份不一致时失败，不能悄悄删去候选。

显式 `semantic` 保留图谱先筛与 Neo4j 精确余弦，方法为 `graph_first_e5_exact_cosine`；`keyword` 保留目录词面检索。hybrid 不可用时的回退必须披露实际模式，不能计为完整三路成功。

## DeepSeek 重排与问答

问答配置只保存在服务端 `.env`；方法见 [LLM 接入说明](LLM接入说明.md)。本地 E5 只编码检索内容，问答调用 DeepSeek API。

RRF 排名后的最多 20 条候选以完整原步骤构成上下文，预算为 **60,000 个 JSON 字符**。超过预算时减少候选前缀并记录遗漏，不静默截断步骤。DeepSeek 重排必须返回输入候选 ID 的完整排列，未知、重复、遗漏 ID 均拒绝；失败时保留检索排名。

重排后选择前 `limit` 条食谱（1～3），为全部原步骤分配 E 证据 ID。DeepSeek 按问题生成带引用的中文段落，程序验证 JSON、ID 归属、引用及数字字面量，保留原步骤、Step、Source 与来源网址。问答失败明确回退原步骤，证据不足返回 `insufficient_evidence`，无有效步骤时不请求重排或问答。

正常检索聊天需要路由、重排、问答三次 API 调用；直接回答只调用一次。须分别查看 `route`、`rerank`、`qa`、`generation.api_calls_attempted` 和 `fallback`，不能把 HTTP 200 当作模型问答成功。

## 接口合同

| 方法与路径 | 主要用途 |
|---|---|
| `GET /api/system/status` | 数据身份、规模、检索与生成状态 |
| `POST /api/search` | 食材条件检索，默认 `hybrid` |
| `GET /api/recipes/{id}` | 原标题、步骤、提及证据与来源 |
| `GET /api/system/graph?recipe_id={id}` | 一条食谱的实际节点、关系与构建身份 |
| `POST /api/generate` | 兼容 API：原步骤组织或明确 `mode=api` 的重排问答 |
| `POST /api/chat` | 提示词、最近历史；路由后直接回答或检索问答 |

搜索默认 `limit=6`（1～20）；生成默认 `limit=3`（1～3）。`query`、生成 `question` 上限为 500 字符；所需与排除食材各最多 20 项，每项 1～80 个可打印字符；显式 `recipe_ids` 最多 3 个。聊天上限另见 [厨神交流](厨神交流.md)。字段及上限不符合合同返回 `422`，不存在的详情返回 `404`。

```json
{
  "question": "找一道用西兰花和胡萝卜做的菜，并根据原步骤说明做法。",
  "ingredients": ["西兰花", "胡萝卜"],
  "excluded_ingredients": [],
  "retrieval_mode": "hybrid",
  "mode": "api",
  "limit": 1
}
```

上例请求 `/api/generate`。其 `mode` 默认仍为 `grounded`，不主动调用模型；网页聊天使用 `/api/chat`。显式提供食谱 ID 时只在所选证据内核验并回答，不能描述为重新运行三路召回。

## 评测与边界

开发机器在真实 Neo4j 上回归 40 条原条件查询，8 条 dev 与 32 条 test 分开。32 条 test 的宏平均 **Precision@10=78.44%、Recall@10=41.65%**，为 DeepSeek 重排前结果；P@10 分母固定为 10，R@10 分母为各题全部自动相关记录。标签来自原始食谱字段的字面条件，不是人工语义标签。

消融核验确认 RRF 改变排名和 Top10 集合，但图谱已经限定完整合法池，多数查询的候选都被条件标签判为相关。因此现有结果不能证明融合优于 E5 或 BM25。检索指标、真实 API 集成和工程引用检查的范围分别见 [公开验收摘要](../reports/发布验收.md)，原始日志不随源码发布。

食材是原文词典规则提及，**不是完整配方表**；原文未提及不等于实际不含，不能保证库存充足、用量、总时长或饮食安全。结构、引用和数字校验不自动证明回答的全部事实语义正确。当前为模型选择两种动作的显式工作流，没有开放式任意工具调用、社区摘要或通用多跳推理。

图片和视频批处理保持停止，已有视觉候选仅用于详情与子图，不进入当前问答上下文。旧 `/api/status`、`/api/graph`、`/api/recommend` 和 CLI 演示使用 20 条手工食谱，不能作为真实数据或模型效果证据。
