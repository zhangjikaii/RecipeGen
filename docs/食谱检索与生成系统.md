# 食谱检索与生成系统

本文说明当前真实 RecipeGen 系统：从已验证的 Neo4j 图谱读取菜谱与证据，组织带引用的回答。旧 20 条人工演示通过另一组兼容接口保留。

源码仓库只保留代码与人工演示小数据，真实图谱、模型和历史详细报告需另行构建。新机器操作顺序见 [README](../README.md)，下文规模是开发机器历史结果，公开摘要见 [发布验收](../reports/发布验收.md)。本文件中的目录检索规则描述关键词分支；当前还支持语义及混合模式，完整方法与字段见 [GraphRAG 设计](GraphRAG设计.md)。

## 数据与实际验收

数据来自 `RUOXUAN123/RecipeGen` 的完整测试文本和媒体目录，固定 revision 为 `2506260d8cb193ecdb18ac31fc725ffec43f6602`，归档白名单为 `test.zip`、`test-video.zip`。基础图谱保存 5,898 条分来源 Recipe、44,802 个有序 Step、296 个规则 Ingredient 实体、46,553 个 Image 和 1,512 个 Video。基础节点和关系分别为 159,040 和 425,687。

Recipe 数量按原归档记录统计，不声称去重为不同菜品。Image/Video 首先是清单，保存原成员、大小和来源定位，不等于已经下载或识别。

[发布验收摘要](../reports/发布验收.md)验证了真实 Neo4j 状态、食材搜索与排除、详情、一个 25 节点/39 关系的菜谱子图、默认 `grounded` 回答与来源校验。该次生成 `llm_called=false`，不是本地模型或语义效果评测。

同日的 [发布验收摘要](../reports/发布验收.md)记录一次真实 `/api/generate` 调用：`llm_called=true`、`fallback=false`，最终模式为 `local_selection_grounded_answer`，已知 ID 选择、原步骤和来源检查全部通过。它是一次功能检查，未测语义准确率。

## 运行与配置

应用环境安装 `requirements.txt` 后，在项目目录执行：

```bash
source .venv/bin/activate
python -m recipegen serve --host 127.0.0.1 --port 8765
```

Neo4j 需先保持可用。连接来自完整 Settings/环境变量，或现有私密 `.runtime/active-neo4j.json` / `.runtime/local-neo4j.json`；JSON 权限要求 `600`。应用不导出密码，不在读取失败后改用手工图谱。入口为 [本地界面](http://127.0.0.1:8765/)与 [API 文档](http://127.0.0.1:8765/docs)。

也可分别运行 `python scripts/manage_recipegen_system.py start`、`status`、`stop` 管理本项目网页服务，默认端口 `8765`。停止操作先核对进程命令与项目工作目录。管理脚本的 `/health` 检查只代表服务响应，不能替代 `/api/system/status` 的图谱范围检查。

启动系统不恢复下载或识别。**图片和视频批处理目前均停止**，接口只读取已有图谱及候选。

## 检索方法

`recipegen/catalog.py` 提供 `status()`、`search()`、`recipe()`、`graph()`。首先验证唯一 `active=true`、`status=verified`、`split=test` 构建及固定 revision。原事实限定在 `recipegen-test-v1` 命名空间；视觉候选限定在同一构建的 `recipegen-mm-v1`。

查询采用固定、参数化 Cypher 和只读事务。菜谱、步骤、来源、食材提及与媒体分别聚合，避免多个列表连接造成数量膨胀；Step 按原非空行顺序返回。读取失败、来源不一致或 ID 不属于当前构建时明确报错。

输入采用小型确定性规则：匹配中英文别名，识别“不要/不吃/不加/排除/without”等否定片段，移出正向查询并合并排除列表。中文问句使用已识别食材；英文短菜名保留标题关键词。多个结构化 `ingredients` 条件都须匹配已有提及；排除条件筛掉有对应提及的候选。`applied_filters` 返回规范名称和 `dictionary_text_mentions_only` 语义。

候选截取前，完整正向查询与菜名相等的记录优先，其次为完整查询是菜名子串的记录，最后按原菜名字母序及稳定 ID 排序；菜名比较忽略大小写和首尾空白。排序仍服从全部关键词、食材提及及排除条件，不将无匹配的查询扩大为全库结果。

这不是完整配方过滤。原文没有提到的食材可能没有抽取，未知别名也可能没有匹配；“未检出”不能证明忌口或过敏安全，“提到全部请求食材”不能证明库存充足。

## 接口合同

| 路径 | 输入与主要输出 |
|---|---|
| `GET /api/system/status` | 数据 ID/revision/test/is_demo、真实数量、系统能力、生成模式与媒体处理状态 |
| `POST /api/search` | `query`、`ingredients`、`excluded_ingredients`、`limit`；返回候选、build、实际过滤与限制 |
| `GET /api/recipes/{id}` | 原 ID；返回标题、步骤、提及证据、来源、媒体清单与已有图像候选 |
| `GET /api/system/graph?recipe_id={id}` | 原 ID；返回该菜谱真实 `nodes`、`edges` 和 build |
| `POST /api/generate` | `question`、可选 `recipe_ids`、食材/排除条件、`mode`、`limit`；返回回答、引用、校验与 trace |

搜索默认 `limit=6`，范围为 1～20；生成默认最多返回 3 条，`limit` 范围为 1～3。`query` 最多 500 字符，`question` 为 1～500 字符。`ingredients` 与 `excluded_ingredients` 各最多 20 项，每项为 1～80 个可打印字符。显式 `recipe_ids` 最多 3 个，仍检查问题中的排除规则；没有 ID 时从真实目录检索。

连接不可用返回 `503`，不存在的详情 ID 返回 `404`；请求字段、结构或上限不符合合同返回 `422`。完整字段以运行中的 `/docs` 为准。

```json
{
  "query": "番茄不要鸡蛋",
  "ingredients": ["番茄"],
  "excluded_ingredients": [],
  "limit": 6
}
```

从检索结果取真实 ID，用于详情与子图。例如验收用过的记录：

```bash
curl 'http://127.0.0.1:8765/api/recipes/recipegen:test:test:34e9f73fe526c3cd800c'
curl --get http://127.0.0.1:8765/api/system/graph \
  --data-urlencode 'recipe_id=recipegen:test:test:34e9f73fe526c3cd800c'
```

## 回答生成与验证

`recipegen/system_generation.py` 默认 `grounded` 模式由程序组织候选。每个步骤保留原文及顺序，绑定 `recipe_id`、`step_id`、`source_id` 和归档路径/URL；原文可能为英文，系统不把自由改写或翻译当成原事实。

```json
{
  "question": "用番茄和鸡蛋能做什么？",
  "ingredients": ["番茄", "鸡蛋"],
  "excluded_ingredients": [],
  "mode": "grounded",
  "limit": 2
}
```

`local` 实现把候选和证据组成有限上下文，通过独立本地进程请求模型选择已知记录与证据 ID。输出经过结构、ID、重复及引用检查，程序再从原记录组装回答。模型不能添加步骤、食材用量、总时长或安全结论。图像描述候选用于详情及子图展示；当前生成模型输入只包含标题、食材提及和步骤摘录，不纳入图像观察。

模型不可用、超时或选择不合法时，程序退回原步骤回答，保留模型错误与回退标记。`validation.passed` 是最终组装检查；模型选择失败另列 `local_selection_valid`，不能用前者掩盖后者。核对 `generation.mode`、`effective_mode`、`llm_called`、`fallback`、`errors`、`trace`。

无候选或没有原步骤时不调用选择模型，不补造做法。已通过的实际 local 功能检查使用 `mlx-community/Qwen3-VL-2B-Instruct-4bit`，固定 revision `9c4f5209e57b31f4b9dfba735de3fb983739c9cc`，MLX 后端、`temperature=0`、`max_tokens=768`、`num_images=0`。模型从一条已检索记录中选择已知 ID，程序返回全部原步骤；此次没有视觉输入，也没有测试自由配方生成或推荐质量。

## 来源与视觉候选

Source 保留数据集、revision、split、归档成员、`artifact_path`、URL。食材提及保留跨度、原文、规范英文名、中文名和步骤 Source；它们是 `dictionary_rule` 候选，没有被提升为完整配料表。

视觉证据按原 `source_media_id` 去重，要求观察、来源和对齐关系属于对应构建与运行。排序使用公开 `state.json` 中已核验成功记录的真实 `finished_at`，只用于选取运行，不表示准确性；没有可核验时间时用稳定 ID 并显示 `latest_unverified`。子图只返回所选图像/运行的候选关系，避免混入旧对齐。

当前保留部分历史图像/视频产物，未完成全量媒体语义处理。2026-10-04 快照中的 3,831 个图像观察对应 2,220 张不同图片；观察数、覆盖数或关系数量不能写成视觉准确率。

## 与兼容演示的区别

旧 `/api/status`、`/api/graph`、`/api/recommend` 和 CLI `demo`、`evaluate` 使用原推荐演示。20 条手工菜谱有为演示填写的主料、调料、用时和标签，能够检查库存、时间、辣味规则；不能把这些字段迁移成真实 RecipeGen 的已知事实。

真实系统使用新接口，回答来自 5,898 条官方测试记录。两套 API 分别保留，真实连接失败不回退演示。旧 50 条功能用例、离线合同测试、实际 Neo4j 验收与模型运行是不同证据。

当前未完成完整用量抽取、配料表验证、总烹饪时长估计、全量视觉/视频处理或语义准确率评测。系统采用显式检索、选择、组装、校验工作流，没有模型自主规划、直接 LLM 对照实验或生产用户指标。
