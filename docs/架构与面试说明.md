# 架构与面试说明

RecipeGen 面向两个任务：按所需及排除食材查找原食谱，以及用中文多轮询问做法。Neo4j 保存 Recipe、Ingredient、Step 和 Source；BM25/E5 排序获取相关食谱，DeepSeek API 负责意图路由、候选重排与证据问答。

## 当前执行流程

```text
探索：用户直接提供所需／排除食材
聊天：问题＋最近历史 → DeepSeek 选择直接回答或检索
                                   ↓ 检索分支
                      独立问题＋所需／排除食材
                        ├─ BM25 全文关键词 → A
                        └─ Cypher 完整图条件池 → C
                             └─ C 内本地 E5 余弦排序 → B
A ∪ B ∪ C → 硬条件复核 → BM25/E5 双排名 RRF(k=60)
  → Top 候选一阶回读食材、全部原步骤与来源
  → 完整有界上下文 → DeepSeek API 重排
  → 选定食谱完整证据 → DeepSeek API 中文回答 → 引用及数字校验
```

探索结束于检索结果，不调用 LLM。聊天直接回答分支只调用一次 API；检索分支成功时调用路由、重排与问答三次。详细合同见 [系统说明](食谱检索与生成系统.md)、[GraphRAG 设计](GraphRAG设计.md)与 [厨神交流](厨神交流.md)。

## 模块职责

| 模块 | 技术与职责 |
|---|---|
| 数据构建 | 保留官方测试文本、归档成员与来源身份，构建 Neo4j 原事实与规则提及 |
| 输入及路由 | 探索表单直接输入条件；DeepSeek 从聊天历史提取独立问题、正负食材及固定动作 |
| 图条件筛选 | 参数化只读 Cypher 检查所需／排除食材，得到完整合法候选池 C |
| 关键词排序 | 原标题和全部步骤建立 BM25；英文别名展开、分词与固定参数 |
| 语义排序 | 本地 multilingual-e5-small 编码问题，384 维，在 C 内精确余弦排序 |
| 融合与证据 | BM25/E5 双排名 RRF；融合后回读完整 Step、Ingredient、Source，验证原文及身份 |
| 重排与问答 | 60,000 JSON 字符预算内保留完整食谱，DeepSeek 排列候选 ID 后依据证据回答 |
| 输出及交付 | 校验 JSON、候选 ID、引用归属与数字，保留明确失败状态；FastAPI 提供 API 与网页 |

## 面试时需要讲清的问题

**为什么用图谱？** 多个所需食材的 AND、别名的 OR 与排除条件可由关系查询直接复核；来源关系还用于确认食谱、步骤和出处属于同一构建。语义相似度没有直接保证硬条件，因此先用图谱限定语义排序范围。但图中只是词典提及，不是完整配料表。

**三路召回是不是三个 RRF 分数？** 不是。A 是 BM25 种子，B 是图谱池内 E5 种子，C 是无序完整图条件集合。C 全量参与并集后，最终合法池由 C 决定；RRF 使用该池的 BM25 正分排名与 E5 排名。图谱没有虚构第三份排名，也不扩大合法范围。RRF 可以改变顺序，但当前评测没有证明这种融合优于单路排序。

**为什么不用全库向量 TopK 再过滤？** 硬过滤可能删掉全库 TopK 中的大部分结果，而符合条件的其他食谱已在召回阶段被截去。先返回全部图条件候选，再给它们计算 E5 分数，使已存在的合法候选都参与排序。它不修复图谱食材漏抽，也不保证 E5 语义质量。

**没有 chunking 能做检索吗？** 可以。当前检索单元是一条食谱，其标题与全部步骤组成 BM25 文档及 E5 passage。Neo4j 保存原步骤，检索后回读全部原文作为生成证据。E5 的 512-token 上限使 95 条长食谱历史编码截断；独立步骤分块 CLI 保留为实验，不替换网页原向量。

**怎样控制模型输出？** 路由只允许固定动作和经过校验的条件；模型不提供 Cypher。重排必须排列所有输入候选 ID，问答只能引用给定步骤证据 ID。上下文超过预算时减少食谱数量而不截步骤；失败明确保留检索顺序或原文回退。引用与数字检查属于工程约束，不等于完整语义正确。

**是不是 Agent？** 当前有 LLM 路由和多轮状态，但检索之后是明确的固定工作流，没有开放式工具规划或多智能体自主协作。可准确描述为知识图谱 RAG、意图路由和证据问答，不声称通用多跳 GraphRAG、社区发现或全局摘要。

## 怎么解释检索指标

32 条原字段自动标注 test 查询的重排前宏平均 Precision@10 为 78.44%、Recall@10 为 41.65%。P@10 固定除以 10，R@10 除以各题全量相关食谱；少于 10 条返回会降低 Precision@10。8 条 dev 单独记录。

真实 Neo4j 消融表明融合会改变结果顺序与集合，但各题相关命中数与 E5 相同。26/32 条查询的整个图条件候选池都被标签判为相关，使该基准主要检查食材条件，难以区分排序质量。下一步需补充做法、偏好等相关性标注与难负例；不能把当前相同指标解释为融合收益。

检索消融、真实 API 集成和源码回归分别记录于 [公开验收摘要](../reports/发布验收.md)。真实 API 一次完整调用证明该次路由、重排、问答及 ID／引用合同通过，不是全量人工问答准确率。源码克隆不会附带开发机器的数据、模型或配置，也不自动意味着已部署。

## 自己实现与调用库

FastAPI、Pydantic、Neo4j Driver 和 E5/DeepSeek 基础模型提供服务、校验、数据库与模型能力。项目实现包括来源绑定、规则规范化、固定条件查询、完整候选池排序与 RRF、证据回读、有界上下文、API 输出校验、回退及实验协议；没有训练或微调基础模型。
