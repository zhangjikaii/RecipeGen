# 架构与面试说明

## 要解决的问题

用户描述的是“我有哪些食材、有什么时间限制、哪些东西不能吃”，图谱保存的是菜谱与食材、步骤、标签、来源之间的关系。RecipeGen 将需求转换为查询条件，检索结构化证据，再生成可检查的推荐。

## 模块职责

| 模块 | 输入与输出 | 技术与作用 |
|---|---|---|
| 图谱载入 | canonical JSON → 节点与关系 | 校验必填字段；存储菜谱、食材、标签、步骤和来源 |
| 条件提取 | 自然语言 / 表单 → 查询条件 | 离线规则或可选 LLM；规范化食材别名与约束 |
| 图谱检索 | 查询条件 → 候选及证据 | SQLite 节点/边关联查询，或 Neo4j 固定查询；过滤时间、食材、忌口 |
| 上下文组织 | 候选 → 限定证据包 | 只提供相关菜谱及来源，减少无关内容 |
| 回答生成 | 证据包 → 候选 ID 与理由代码 → 推荐说明 | 默认模板；可选 LLM 做结构化选择；原始事实由程序组装 |
| 输出验证 | ID/理由代码＋证据 → 校验结果 | 检查候选归属、理由适用与条件满足；失败时回退或说明 |
| 交付与评测 | API / CLI / 网页 → 演示与报告 | FastAPI、Pydantic、可复现评测用例 |

具体字段与行为以代码和运行报告为准。原 Neo4j schema 需先核对后才能迁移或适配。

## 什么是这里的图谱 RAG

```text
“番茄和鸡蛋，20分钟内，不吃辣”
       ↓ 提取约束
食材=[番茄, 鸡蛋]，时间≤20，禁辣
       ↓ 关系检索与条件筛选
菜谱 → 使用食材 / 标签 / 步骤 / 来源
       ↓ 组织证据
候选菜谱内容＋关系证据＋来源标识
       ↓ 可选模型选择
候选 ID 与限定推荐理由代码
       ↓ 程序组装
推荐、原始步骤、食材、时间与来源
       ↓ 程序检查
可追溯的结果或无匹配原因
```

这个项目使用已有领域关系检索证据，不依赖向量相似度。它没有实现 GraphRAG 的社区发现、全局摘要或大型多跳推理。未配置模型时只能证明图谱检索与验证流程运行，不能据此声称真实 LLM 已有效使用图谱。

## 哪些是库，哪些是项目逻辑

- **使用的库**：FastAPI 负责 HTTP 服务，Pydantic 负责数据校验，Neo4j Python Driver 负责数据库通信，SQLite 提供本地持久化。
- **项目逻辑**：食谱字段定义、需求解析、别名规范化、条件筛选、候选排序、证据组织、提示词、生成结果校验、回退和评测规则。
- **大模型能力**：理解措辞、提取条件及组织自然语言；模型本身没有被训练或微调。

向面试官说明自己理解、维护和验证了哪些模块；不要把调用库说成独立研发数据库或大模型。

## 面试可以怎样讲

**为什么选图谱？** 食谱具有清楚的实体与关联，且需求包含确定的条件。图谱适合追溯“这道菜用了什么食材、有哪些标签、对应哪条来源”，程序可以直接检查条件。

**为什么不直接问 LLM？** 推荐需要符合现有数据和用户条件。系统先获取图谱记录作为生成依据，再校验输出。是否优于直接模型，需要使用相同问题和模型做真实对照才能结论。

**如何控制幻觉？** 限制上下文为检索结果，要求输出候选 ID 与允许的理由代码，检查候选归属及条件，原始步骤、时间和来源始终由程序返回。保留失败与回退记录。这避免模型自由改写关键事实，但不能保证原图谱数据或模型条件解析绝对正确。

**怎么体现 context engineering？** 区分原始需求、明确约束、证据内容和输出格式；仅加入相关记录；检索资料属于数据，不作为系统指令；生成后按证据再次检查。

**是不是 Agent？** 当前是可验证的固定工作流。只有进一步增加模型自主选择工具、根据执行结果决定下一步，并评测这种决策行为，才有依据强调 Agent 自主执行。

**如何处理没记录的时间/辣度？** 缺失信息不能解释成“符合条件”。数据接入时明确字段要求，缺少必要内容就拒绝或补齐真实资料；涉及筛选的标签需要核对，模型不能填出一个看似合理的数值。

## 三类验证必须分开

| 层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 离线示例、单元测试与 API 演示 | 项目在指定示例范围内运行，约束和引用检查通过 | 真实图谱规模、真实模型效果、真实用户满意度 |
| 实际 Neo4j 连接与数据核验 | 指定数据库的结构、读写适配及检索行为 | 模型生成是否可靠 |
| 实际 LLM 调用与保留评测报告 | 指定模型与数据上的解析、生成、失败率和耗时 | 换模型、换数据或生产负载上的效果 |

演示集为人工编写，评测用例也由项目设计。评测指标有开发偏差；拿到真实图谱后应加入独立整理的测试问题，覆盖别名、否定表达、多重约束、无结果和缺失字段。

## 后续真实实验

1. 记录原图谱构建方式、数据来源、菜谱/实体/关系规模和抽样核验结果。
2. 固定真实测试问题和标准答案；划出开发与最终评测部分。
3. 比较同一个模型的直接回答、图谱增强回答，保持模型设置和测试问题一致。
4. 统计检索召回、约束满足、引用正确、任务完成、生成失败及耗时。对每种指标明确分母和检查办法。
5. 保存输入、候选证据、输出、验证结果、模型配置和运行时间；没有发生的实验不写结论。
