# 食谱探索与厨神交流

网页使用统一首页 `/`，只显示“食谱探索”和“厨神交流”两个选择，保留品牌配色与主题切换。选择后在主入口显示对应工作区，可切换模式或返回首页；移除大图、介绍段落和多余小字。旧地址 `/explore`、`/compose` 继续兼容。

## 食谱探索

`/?view=explore` 只有“想用的食材”和“不想用的食材”两个输入框。提交后直接请求 `/api/search`，固定使用 `hybrid`，按三路候选 → 条件核验 → RRF → 图谱证据回读返回食谱。卡片可以打开原始步骤与来源详情，不再选择食谱或切换检索方式。该入口不调用 LLM。

## 厨神交流

`/?view=chat` 是多轮聊天工作区，显示厨神头像、消息记录和提示词输入框。用户无需提供独立食材字段、选中食谱或选择问答方式。可以开启新对话；完成的消息保存在当前标签页的 `sessionStorage`，探索结果与聊天状态独立。

发送内容通过新 `POST /api/chat`：

```json
{
  "message": "推荐同时使用西兰花和胡萝卜、不放花生的菜，说明关键做法。",
  "history": [
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好，今天想做什么？"}
  ]
}
```

输入上限：当前消息 1–1000 字符；历史最多 20 条、每条 1–4000 字符；消息和历史合计最多 20000 字符。只允许 `user`、`assistant` 两种历史角色，拒绝额外请求字段。前端在预算内保留最近完成的对话；失败或取消的回答不会作为成功的助手消息传入下轮。

## LLM 路由与回答

`recipegen/chef_chat.py` 的 `ChefChatService` 先请求已有 DeepSeek API，结合当前问题和历史返回两种固定动作之一：

1. **`respond`**：普通烹饪技巧、闲聊或需要澄清的问题，直接返回简短中文回答。只调用一次 API，不查询图谱，不展示虚构引用；响应标为 `answer_basis=general_model_knowledge`。
2. **`retrieve`**：找菜、推荐具体食谱或追问推荐食谱事实。模型将追问改写成无需历史即可理解的独立问题，并提取本轮生效的所需／排除食材。接着执行BM25／图谱先筛 E5／图谱条件三路 → 候选核验与 RRF → 图谱证据回读 → 有界上下文 → 最多 20 候选 DeepSeek 重排 → 前 3 条食谱完整步骤问答 → 引用与数字校验。正常成功时共调用三次 API：路由、重排、问答。响应标为 `answer_basis=retrieved_original_recipe_steps`。

最新明确要求覆盖旧条件；“可以放花生”表示撤销排除，不表示必须放花生。聊天检索以模型提取的正负食材数组作为硬条件，`infer_query_filters=false`，独立问题用于 E5 排序和最终问答；BM25 正向食材采用生产别名扩展，没有正向食材时采用独立问题词面，避免字面提及把可选食材变成必需条件。探索与兼容旧接口仍按原规则解析查询。模型只输出严格校验的 JSON 动作、查询和有界食材列表，不能提供 Cypher、工具名称、食谱 ID 或 API 地址。图谱只读且仍核对构建、原文和来源身份。

检索回答每段可展开引用原始步骤、Step、Source 与来源网址；普通回答不展示引用。消息中的模型文本通过 DOM `textContent` 渲染，不执行 HTML。

## 返回与失败

成功响应保留 `status`、`answer`、`route`、`generation`、`trace`、`evidence`、`paragraphs`、`recipes`。检索分支另有 `retrieval`、`rerank`、`qa`、`validation`；`route.history_messages` 显示本次使用的历史条数。`generation.api_calls_attempted` 含路由请求，不能把 HTTP 200 或路由成功当作重排问答也成功。

API 未配置或图谱／E5 不可用返回安全 `503`；路由无效或上游失败返回 `502`；请求合同不符返回 `422`。错误内容不回传供应商原始响应或凭据。无合格食谱时不请求重排或证据问答；问答失败不伪造聊天答案，界面允许重试。检索引用校验沿用 [GraphRAG 设计](GraphRAG设计.md)。

兼容的 `/api/generate` 保留原有 `grounded`、`local`、`api` 请求合同；新网页不再显示这些模式。配置仍沿用本地 `.env` 的 DeepSeek API，E5 保持本地编码器，不重建知识图谱或向量。

## 验证边界

页面模拟接口检查与真实 API 集成分别验证。开发机器的三路链浏览器检查使用模拟 API；一次真实聊天确认 DeepSeek 路由、重排、问答均成功，没有回退。源码回归、公开页面截图及具体执行范围见 [公开验收摘要](../reports/发布验收.md)。原始运行报告、私密配置和真实语料不随源码发布。

工程与引用检查不能代替人工语义相关性或问答准确率；原字段自动标签的 P@10、R@10 位于 DeepSeek 重排前，不能用于证明路由、重排或回答效果。新环境需重建图谱、E5 索引和配置，不能仅靠源码克隆复现开发机器的运行状态。
